# Rust移植設計案

この文書は新実装への提案であり、原版で確認した仕様は [互換仕様書](WCASL2_COMPATIBILITY_SPEC.md) に分離する。

## 1. 最初に固定する互換対象

「CASL II対応」だけでなく、対象SHA-256を持つWCASL2の挙動を基準にする。汎用的なCOMET II VMを作って画面を付けるだけでは、次が抜ける。

- 3000語メモリ、0020ロード、FFFF初期化、ロード結果に応じたSP。
- 12語のIN/OUT、14語のRPUSH、7語のRPOPと表示行の対応。
- 空行の扱い、DC負数・文字列・ラベル検査の癖。
- 画面出力の44桁×12行、画面とファイルの改行差。
- 4フェーズと命令ごとに異なる最小STEP数。
- 再実行を用いたBackspaceと入出力の副作用。

## 2. UIから独立したRustコア

```text
workspace/
  crates/
    casl-source/       CP932、行分割、字句、診断、互換モード
    casl-assembler/    2パス、ラベル、リテラル、マクロ、中間情報
    casl-linker/       複数プログラム、外部公開名、再配置、ロード配置
    comet-core/       CPU、3000語メモリ、マイクロステップ、状態遷移
    comet-session/    入出力イベント、再実行、タイマー要求、停止
    wcasl-project/    cas/cmk、保存設定、パス解決
  apps/
    desktop-egui/     または desktop-tauri/
  compatibility/
    cases/            入力と期待結果
```

これは論理分割であり、初期段階からすべて別crateにする必要はない。特にCPUコアはGUIやファイルダイアログを呼ばず、入力要求・出力イベントを返す設計にする。

## 3. データモデル

```rust
pub struct Cpu {
    pub gr: [u16; 8],
    pub sp: u16,
    pub pr: u16,
    pub fr: Flags,
    pub ir: [u16; 2],
    pub decoder: DecodedFields,
    pub mar: u16,
    pub mdr: u16,
    pub effective_address: u16,
    pub call_depth: u32,
}

pub struct Machine {
    pub cpu: Cpu,
    pub memory: Memory,
    pub phase: Phase,
    pub micro_step: u8,
    pub halt: Option<HaltReason>,
}

pub enum StepMode {
    Micro,
    Phase,
    Instruction,
    ToEnd,
    ToAddress(u16),
}

pub enum SessionEvent {
    NeedInput { buffer: u16, length_cell: u16 },
    DisplayByte(u8),
    FileRecord(Vec<u8>),
    Halted(HaltReason),
}
```

`Memory` は3000語の配列を包み、`read` の範囲外はFFFF、`write` の範囲外は無視する互換アクセサを持つ。Rust配列の添字にu16を直接使わない。アドレス加算は `wrapping_add` 等で16ビット化する。

算術の符号は `u16 as i16` と、桁あふれ判定用の広い整数を明確に分ける。一般のRustシフトをそのまま使わず、対象EXEが使う「(n−1)&31、その後1ビット」の手順を互換関数に閉じ込める。

## 4. ソースから表示までの対応

アセンブル結果は機械語だけにしない。少なくとも次を保持する。

| 情報 | 使用先 |
|---|---|
| ファイル、プログラム、元の行番号 | エディタへ移動、診断表示 |
| 元のラベル・命令・オペランド | CASL表示、原版の表示再現 |
| 開始番地と語数 | ソース行と機械語の対応 |
| マクロ展開の各命令 | COMET表示、途中STEP |
| ラベルのスコープと公開名 | リンク、ラベル一覧 |
| リテラルの元表記 | =1と=#0001を別に扱う共有規則 |
| DSの範囲 | 初期化・非書込・表示の区別 |
| 再配置対象 | リンク後の語の更新 |

内部配列を原版と同じサイズで危険な形にする必要はない。互換上の上限は明示的なエラーで扱い、使われていないメモリまで破壊する実装は避ける。

## 5. 最小STEPを唯一の状態更新元にする

`step_micro()` を基礎にし、フェーズSTEPと命令STEPはその繰り返しで構成する。命令実行を別の高速関数として二重実装すると、COMET画面の中間状態と通常実行の結果がずれる。

マイクロステップは更新された値に加えて、強調表示用の情報を返す。

```text
MicroEvent {
  phase,
  phase_index,
  changed_registers,
  memory_read,
  memory_write,
  active_bus_segments,
  active_decoder_fields,
  current_source_location,
}
```

PR→MARなどの描画をUIが独自に推測しない。元コードの描画フラグを意味に置き換えて、UIの座標とCPU処理を分離する。

## 6. 入出力と戻る操作

キーボードの入力結果を `Record(Vec<u8>)` と `Eof` に分ける。空レコードとEOFは同じ値にしない。

CP932バイト列、DC時の符号拡張、IN時のゼロ拡張、OUT表示のフィルタを、それぞれ独立した処理にする。すべてをUnicode文字列の共通変換に通すと原版の差が失われる。

戻る機能には、CPU・メモリ・Display・入力消費位置・CALL深さ・フェーズを含める。実装方法は次の選択がある。

| 方法 | 特徴 |
|---|---|
| 原版同様にリセットして再実行 | 原版へ近づけやすいが、入力やファイル出力が再発する |
| 状態スナップショットと差分 | 高速で外部I/Oを再送しない。ただし原版と意味が変わる可能性 |
| 定期スナップショット＋入出力イベントの記録 | 長時間実行の復元と決定的な再生を両立しやすい |

最初は入力をイベントとして記録し、外部ファイル書込をUI側で実行する設計にしておく。追加解析で、原版のBackspaceは再実行中にキーボード入力を求め直し、違う入力を受理することを実機確認した。旧版互換モードでは、過去の入力を自動再利用するだけの設計では一致しない。再入力待ちを状態として表し、UIが応答を返してから再実行を継続する。

決定的な入力再生を提供する場合は改善モードの仕様として分ける。ファイルOUTは再実行時に再Open・再Writeするが、最初のOUTより前へ戻すと旧ファイル内容が残ることを実ディスクで確認した。外部ファイルのトランザクション巻き戻しを旧版の機能として実装しない。短い出力では付加LFがCRLFとなり、Closeまでサイズ0だった。NULを含む出力はその位置で終端し、後続の付加改行も失われる。長い出力と装置切替は継続課題。

cmkでは、現在開いているファイルパスと内部に保存されたパスを別に保持する。旧版の「保存」ボタンが内部の旧パスへ書くこと、3番目をメインにすると表示名とパスの順序がずれることを実機確認した。読み込んだ旧cmkのフィールドは保持し、表示名からパスを作り直すなどの暗黙の修復をしない。通常のUIではファイル名・パスを組で動かし、旧形式のまま保存する場合の扱いを明示する。

欠損ファイルで旧版はfopenの失敗を検査せず終了する。移植では同じ失敗条件を診断として返し、アプリのプロセスを落とさない。相対パスも通常はプロジェクト基準に固定し、旧版のカレントディレクトリ依存を再現する場合は互換設定として分ける。

## 7. Tauri / eguiの選び方

以下はこのアプリの構造に基づく設計判断で、特定バージョンの機能・速度の実測比較ではない。

| 観点 | Tauri案 | egui案 |
|---|---|---|
| ソースエディタ | Webのエディタ部品を組み込みやすい構成 | 編集機能をRust側のUIで用意 |
| COMETの図 | SVG/Canvas等で描画し、Rustコアのイベントを反映 | Rustコアの状態から直接描画 |
| データ受け渡し | コアとWeb表示の間のコマンド・差分通知を設計 | Rustの型をそのまま利用しやすい |
| 原版の複数文書 | タブ・ペインとして再構成する案 | タブ・ペイン・フローティング領域として再構成する案 |
| 開発の中心 | 編集体験・検索・補完・Web UIを重視する場合 | CPU図・ステップ操作・Rustでの一体的な試作を重視する場合 |

まず共通コアと互換データを作れば、選択を後から変えられる。授業用シミュレータの核を先に再現する段階ではeguiの薄い検証画面、編集体験を主眼に完成させるならTauriという進め方が考えられる。フレームワークの採用版・対応OS・配布方式は、実装着手時に別途決める。

Tauri案では毎マイクロステップで3000語全体を送らず、変更差分と表示範囲を送る。連続実行時の通知を描画周期へまとめる。egui案でも、画面更新とCPUの進行を分離し、1フレームで無制限に実行しない。

## 8. 移植の順序

| 段階 | 成果物 | 合格基準 |
|---|---|---|
| 1 | ヘッドレスCPU、メモリ、命令 | cpu_casesの比較。標準演算980件も再確認 |
| 2 | 最小STEPと中間状態 | pipeline_casesの状態列が一致 |
| 3 | 単一プログラムのアセンブラ | 機械語・診断・リテラル配置が一致 |
| 4 | 複数プログラムとリンク | build_casesの外部名、入口、配置が一致 |
| 5 | DisplayとIN/OUT | バイト、LEN、カーソル、EOF、折返しが一致 |
| 6 | CASL表示 | ソース/語/ラベル/スタックの対応と操作 |
| 7 | COMET表示 | 最小STEP、フェーズ、データパス強調 |
| 8 | Undo、時間実行、手動編集 | 実機の未確定ケースを埋めて比較 |
| 9 | cmk・設定移行・配布 | 原版保存ファイルの相互検証 |

原版の不具合を改善する変更は、互換モードの金データを維持した上で追加する。空行許容、UTF-8対応、メモリ拡張、長いシフト量の一般化、UI応答性改善などを、根拠なく旧版の挙動として扱わない。
